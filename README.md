# 1. API 상태 기반 사용자 피드백 개선
관련 이슈: Issue #6

## 리팩토링 이유
기존에는 API 요청 실패를 console.log나 alert()로 처리하고 있어, 사용자는 화면이 비어 있는 이유를 알기 어려웠습니다.
또한 요청 중, 데이터가 없는 경우, 오류가 발생한 경우가 별도의 상태로 구분되지 않아 모든 상황이 비슷한 빈 화면으로 보일 수 있었습니다.

## 기존 방식
- API 요청 상태를 별도로 관리하지 않음
- 로딩 중에도 기존 화면이나 빈 영역이 표시됨
- 오류 내용을 개발자 콘솔 중심으로 처리
- 데이터가 없는 상태와 요청 실패 상태를 구분하지 않음
- 사용자가 실패한 요청을 다시 시도하기 어려움

## 변경 방식
1. 공통 AsyncStatus 타입을 정의해 API 요청 상태를 명시적으로 구분했습니다.
```
- idle: 요청 전
- loading: 요청 중
- success: 요청 성공
- empty: 요청은 성공했지만 데이터가 없음
- error: 요청 실패
```

2. 영화 및 컬렉션 화면이 현재 상태에 맞는 UI를 렌더링하도록 변경했습니다.
- 로딩 중 Skeleton UI 표시
- 실패 시 Ionic Toast와 재시도 버튼 제공
- 데이터가 없을 때 Empty State 표시
- 이미지 로드 실패 시 기본 이미지로 대체
- 개발 환경에서 Mock 응답 지연을 적용해 로딩 UI 확인
  
3. 변경 결과
- 네트워크 요청 중 화면이 비어 보이는 문제를 보완했습니다.
- 사용자가 로딩·빈 결과·오류 상태를 구분할 수 있게 됐습니다.
- 요청에 실패해도 페이지를 새로고침하지 않고 다시 시도할 수 있게 됐습니다.
- 컴포넌트에서 비동기 요청의 상태 전환을 명확하게 확인할 수 있게 됐습니다.
- 영화와 컬렉션 화면이 공통된 상태 표현 방식을 사용하게 됐습니다.

# 2. 온보딩 상태 관리 및 사용자 흐름 개선
관련 이슈: Issue #8

## 리팩토링 이유
온보딩 완료 여부와 선택 장르를 판단하는 로직이 Recommendation, Home, Mypage 등 여러 컴포넌트에 분산되어 있었습니다.
각 컴포넌트가 직접 상태를 확인하고 페이지를 이동시키면서, 새로고침이나 URL 직접 접근 시 사용자 상태에 맞지 않는 화면이 노출될 가능성이 있었습니다. 또한 추천 화면이 영화 선택뿐 아니라 인증 확인과 페이지 접근 판단까지 담당하고 있었습니다.

## 기존 방식
- 여러 컴포넌트가 온보딩 완료 여부를 각각 판단
- 컴포넌트가 인증 상태 확인과 화면 이동까지 담당
- 페이지에 진입한 이후 다른 화면으로 리다이렉트
- 완료 여부와 선택 장르의 상태가 분리되어 관리
- 마이페이지 진입 시 추천 화면으로 이동하는 중복 로직 존재

## 변경 방식
1. 온보딩 상태 판단과 완료 처리를 OnboardingService로 분리했습니다.
  
2. Recommendation 컴포넌트는 다음 역할에만 집중하도록 단순화했습니다.
- 영화 목록 표시
- 영화 선택 및 해제
- 선택 결과를 기반으로 선호 장르 계산
- 온보딩 완료 처리 요청

3. Angular의 기능형 Route Guard도 적용했습니다.
- 비로그인 사용자의 온보딩 접근 제한
- 온보딩 미완료 사용자의 홈 접근 제한
- 완료 사용자의 온보딩 화면 재진입 방지
- 기존 /recommendation 경로를 새로운 경로로 연결

## 변경 결과
- 컴포넌트에 분산된 상태 판단과 이동 로직을 서비스와 라우터로 분리했습니다.
- 페이지가 렌더링되기 전에 Route Guard가 접근 가능 여부를 판단하게 됐습니다.
- 새로고침과 URL 직접 접근에도 동일한 화면 이동 규칙을 적용했습니다.
- 추천 컴포넌트에서 인증 및 사용자 조회 등 불필요한 책임을 제거했습니다.
- 온보딩 상태 저장 방식이 변경되더라도 컴포넌트에 미치는 영향을 줄일 수 있는 구조가 됐습니다.
